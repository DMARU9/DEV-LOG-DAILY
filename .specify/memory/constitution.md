# Dev Log Daily Constitution

## Core Principles

### I. ツール型アーキテクチャ
すべてのデータソース（チャットログ、Gitコミット、ターミナルログ等）への対応はプロダクトに内蔵されたツールとして実装する。各ツールは独立したインターフェース（collect/parse）を持ち、互いに分離されて動作する。新たなデータソースを追加する際は本体コードの修正が必要であり、外部からの動的ロードやユーザーによる追加・選択は不可とする。これによりシステムの予測可能性と安定性を確保する。

### II. オフライン・ローカル優先
個人の開発環境内で全ての処理が完結することを最優先とする。外部クラウドサービスへの依存は、ユーザーが明示的に有効化しない限り行われない。収集したログ・生成した日報はローカルに保存され、常にユーザーの制御下にあることを保証する。

### III. エージェント毎のLLM選択
各コンポーネント（Collector、Enricher、Reporter等）は独立したLLMモデルを選択可能とする。システム全体で単一のLLMに依存せず、コンポーネントの役割や処理内容に最適なモデルを構成できること。設定ファイルでコンポーネント毎のモデル指定をサポートする。

### IV. 設定駆動型
ユーザーは設定ファイル（YAML/TOML/JSON等）を通じて、データソース、LLM選択、レポート形式、出力先などをコード変更なしにカスタマイズ可能とする。設定値はスキーマ定義により検証され、誤った設定は起動時に明確なエラーメッセージで報告する。

### V. 日本語ドキュメント・コメント
プロジェクト内のすべてのドキュメント（README、設計書、API仕様）とコードコメントは日本語で統一する。公開インターフェースの説明も日本語を第一言語とする。ただし、外部公開パッケージのメタデータ（package.json 等）や業界標準の用語（JSON、YAML、CLI等）はこの限りではない。

### VI. テスト実装の義務付け
すべての機能追加・変更には対応する単体テストおよび結合テストを実装しなければならない（MUST）。テストがないコードはリリース不可とする。各データソースツールには結合テストが必須であり、実際のデータ形式を使用したテストケースを含めること。

## 開発ワークフロー

### ブランチ戦略
- 機能開発は feature ブランチで行い、develop ブランチへのマージは PR ベースとする
- コミットメッセージは日本語で記述し、変更内容を明確に説明すること

### 品質ゲート
- すべてのテストが成功しなければマージ不可
- コードレビューでは憲法の各原則への準拠を確認する
- 各機能開発サイクルの計画フェーズで憲法との整合性レビューを実施する
- コミット前に pre-commit フックを実行し、すべてのチェックが成功することを確認しなければならない（MUST）。pre-commit が失敗した状態でのコミットは禁止する
- `--no-verify` や `--force` 等の pre-commit をバイパスするオプションを付けたコミット、および強制プッシュ（`git push --force`）は禁止する。これらは品質ゲートの回避とみなし、憲法違反とする
- Python コマンドの実行は仮想環境（`.venv` 等）内で行わなければならない（MUST）。システムのグローバル Python インタプリタを使用しての実行は禁止する。これにより依存関係の分離と再現可能な実行環境を保証する

### リリース
- バージョニングはセマンティックバージョニング（MAJOR.MINOR.PATCH）に従う
- CHANGELOG は日本語で記述する

## データ管理とプライバシー

### データ保存
- 収集したログデータはローカルファイルシステムに保存し、ユーザーがいつでも削除・エクスポート可能とする

### プライバシー
- 外部サービスにデータを送信する機能はデフォルトで無効とし、ユーザーが明示的に有効化する設計とする
- 送信するデータの内容と送信先をユーザーが事前に確認できる仕組みを提供する

## Governance

本憲法はプロジェクトのすべての実践に優先する。改正には以下の手順が必要である：
1. 改正案の文書化：変更内容と理由を明確に記述する
2. 合意形成：プロジェクトメンバー間での承認を得る
3. 移行計画：既存の実践との整合性を確保する移行手順を策定する

準拠性のレビューは各機能開発サイクルの計画フェーズで実施する。憲法に反する実践が発見された場合は、是正計画を文書化し、次サイクルまでに対処する。
