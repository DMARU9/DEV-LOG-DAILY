# Feature Specification: 開発活動ログ自動収集・日報生成フレームワーク

**Feature Branch**: `001-auto-daily-report`

**Created**: 2026-06-20

**Status**: Draft

**Input**: User description: "開発者は毎日複数のツール（Git、IDE、Issue、Terminal等）を使って作業を進めるが、活動ログは分散している。これらのログから日報を自動生成することで、学習記録の作成手間を削減し、個人の成長を可視化したい。複数のデータソースから開発活動を自動収集し、LLMで構造化・要約して日報を生成するフレームワーク。"

## Clarifications

### Session 2026-06-20

- **Q**: パイプラインのオーケストレーション方式は何を使うか？ → **A**: LangGraph StateGraph（継続）を採用。既存のprototypeと同様、StateGraphで各ノードを定義し、状態を共有しながら順次実行する。
- **Q**: データソースツールの構成方式は？ → **A**: ツールはプロダクトに内蔵固定とし、ユーザーによる追加・選択は不可。各データソース（Copilotチャット、Gitコミット、ターミナル履歴）に対して1つのツールのみ存在する。
- **Q**: LLM障害時の回復戦略は？ → **A**: エラー種別により動作が異なる。永続エラー（認証失敗401、不正リクエスト400/403等）は即時停止。一時的エラー（レート制限429、サーバーエラー5xx）は指数バックオフで最大3回リトライし、全リトライ失敗後にパイプラインを停止する。部分的な収集結果は破棄せずに保持するが、日報生成までは進めない。
- **Q**: 同名の日報ファイルが既に存在する場合の出力方法は？ → **A**: 常に上書きする。
- **Q**: 設定ファイルの形式は？ → **A**: YAMLに統一する。
- **Q**: LLMのトークン制限超過時の挙動は？ → **A**: 分割・要約して処理する。トークン制限を超える場合、データを複数チャンクに分割し各チャンクを個別に要約した後、統合して最終的な日報を生成する。
- **Q**: 日付境界のタイムゾーン判定基準は？ → **A**: システムのローカルタイムゾーンを使用する。OSのタイムゾーン設定に従い、ユーザーによる追加設定は不要。
- **Q**: 出力ディレクトリが存在しない場合の挙動は？ → **A**: 出力ディレクトリは設定ファイルに必須記載項目とする。設定ファイル読み込み時に出力ディレクトリが存在しない場合はエラーメッセージを表示して終了する。自動生成は行わない。
- **Q**: パイプライン実行中の進捗表示方法は？ → **A**: 標準出力に逐次ログを出力する。各ノードの開始・終了・エラーを標準出力に表示し、詳細ログはファイルにも出力可能とする。
- **Q**: Enricherコンポーネントの責務は？ → **A**: 不足情報の補完と整合性チェック。各データソースの解析結果をクロスリファレンスし、矛盾点の指摘や欠落情報の補完、コンテキストの付与を行う。
- **Q**: 日報の対象期間は？ → **A**: 単一日付のみ。デフォルトは前日、CLIオプション `--date` で任意の単一日付を指定可能。複数日の期間指定や週次サマリーは範囲外とする。
- **Q**: 巨大ログファイルの処理タイムアウトは？ → **A**: 設定可能なタイムアウト（デフォルト600秒）＋分割処理。ファイル処理にタイムアウトを設け、タイムアウト時は処理済み部分までのデータを採用し、後続のLLM投入時に分割要約される。
- **Q**: コンポーネント未指定時のLLMモデルフォールバック戦略は？ → **A**: 全コンポーネントにモデル指定を必須とする。未指定がある場合は起動時エラーとする。フォールバックは行わない。- **Q**: LLM APIの一時的エラー（レート制限429、サーバー過負荷503等）に対するリトライ戦略は？ → **A**: エラー種別を区別する。永続エラー（認証失敗401、不正リクエスト400、403等）は即時停止。一時的エラー（429、5xx）は指数バックオフで最大3回リトライする。全リトライ失敗後は該当LLM呼び出しの失敗としてパイプラインを停止する。- **Q**: 日報ファイルの命名規則は？ → **A**: `daily_report_YYYY-MM-DD.md` とする。既存prototypeと互換性を維持する。
- **Q**: 設定ファイルのデフォルト検索パスは？ → **A**: デフォルト検索は行わない。CLIオプション `--config` でパスを明示的に指定することを必須とする。指定がない場合は起動時エラーとする。
- **Q**: LLM APIキー・認証情報の管理方法は？ → **A**: YAML設定ファイルの `llm` セクションに `api_key` フィールドを設け、設定ファイルに直接記述する。環境変数による受け渡しは行わない。

- **Q**: 同名日報ファイル存在時の上書き確認は必要か？ → **A**: 不要。常に上書き（現行の spec 通り）。CLIツールとしてのシンプルさを優先する。
- **Q**: データソースパスの指定方法は？ → **A**: 設定ファイルでの明示指定のみ。自動検出ロジックは持たず、未指定は起動時エラーとする。
- **Q**: 出力ディレクトリが存在しない場合、自動生成するか？ → **A**: 自動生成しない。現行の spec 通り、エラーメッセージを表示して終了する。
- **Q**: 日報出力の文字コード・改行コードは？ → **A**: UTF-8 / LF固定。文字コードはUTF-8、改行コードはLF（Unix）で統一する。
- **Q**: 日報のMarkdown出力構造はどこまで固定するか？ → **A**: トップレベルセクション（概要、使用技術、学習内容、開発活動、発生した問題と解決策）のみ spec で固定する。詳細内部構造や各セクションのサブ項目は LLM プロンプトの設計に委ねる。
- **Q**: データソースツールの有効/無効は設定可能か？ → **A**: 不可。3ツールすべてが常に実行される。有効/無効の設定項目は設けない。
- **Q**: FR-014（ログ保持期間）の具体的な動作は？ → **A**: FR-014 を削除する。ログ保持期間の機能は実装せず、ログの管理はユーザーの手動管理に委ねる。憲法第II条（オフライン・ローカル優先）に基づき、自動削除による意図しないデータ消失リスクを回避する。
- **Q**: Enricher コンポーネントの障害時動作は？ → **A**: Enricher の LLM 呼び出し失敗は他の LLM エラーと同様に扱う。指数バックオフリトライ（最大3回）後も失敗した場合はパイプラインを停止する。収集・解析済みのデータは保持するが、日報生成までは進めない。Enricher をスキップして Reporter に進むことはしない。
- **Q**: Gitコミット収集の対象範囲は？ → **A**: 設定ファイルで親ディレクトリ（例: `F:\TAKUMI\knowledge\logs`）を1つ指定する。システムはその配下を再帰的に探索し、すべての Git リポジトリを自動検出してコミット履歴を収集する。
- **Q**: CLI コマンド名とインストール方法は？ → **A**: パッケージ名は `dev-log-daily`、CLI コマンド名は `dev-log-daily` とする。`pip install dev-log-daily` または `uv tool install dev-log-daily` でインストール可能とする。実行例: `dev-log-daily --config config.yml`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 日次レポートの自動生成 (Priority: P1)

開発者がCLIコマンドを一度実行するだけで、前日の開発活動（GitHub Copilotチャット、Gitコミット、ターミナル操作履歴）が自動収集・解析され、構造化されたMarkdown形式の日報が生成される。開発者は日報を手作業で書く手間から解放され、生成された日報をそのまま学習記録やブログ素材として活用できる。

**Why this priority**: 本フレームワークの核心価値である「日報生成の自動化」を実現する最小機能。これがなければ他のデータソース追加やカスタマイズ機能の価値が発揮されない。

**Independent Test**: CLIコマンドを実行し、前日の実際の開発ログから日報が生成され、指定された出力先にMarkdownファイルが保存されることを確認する。

**Acceptance Scenarios**:

1. **Given** 前日にGitHub Copilotとのチャット履歴、Gitコミット、ターミナル操作履歴が存在する, **When** ユーザーが日報生成CLIコマンドを実行する, **Then** 前日分の全ログが自動収集され、LLMにより構造化された日報（Markdown形式）が生成され、所定の出力ディレクトリに保存される
2. **Given** 前日のログが一部のデータソースにしか存在しない, **When** ユーザーが日報生成を実行する, **Then** 存在するデータソースのみから日報が生成され、欠落したソースについては「該当なし」と明示される
3. **Given** 前日のログが全く存在しない, **When** ユーザーが日報生成を実行する, **Then** 「対象データがありません」という明確なメッセージが表示され、エラー終了せずに処理が完了する
4. **Given** LLM APIが応答しないまたはエラーを返す, **When** 日報生成が実行される, **Then** どの処理段階で失敗したかがエラーメッセージで報告され、パイプラインはその時点で停止する。ただし、エラー発生前に収集・解析済みの部分データは破棄せずに保持する

---

### User Story 2 - 設定ファイルによるカスタマイズ (Priority: P2)

ユーザーがYAML形式の設定ファイルを通じて、各コンポーネントで使用するLLMモデル、日報の出力形式・出力先などをコード変更なしにカスタマイズできる。

**Why this priority**: 憲法第IV条（設定駆動型）に準拠するため。ユーザーが自身の環境や好みに合わせてフレームワークを調整できることは、個人開発者向けツールとして重要な価値を持つ。

**Independent Test**: 設定ファイルを編集してデータソースやLLMモデルを変更し、日報生成を再実行して変更が反映されることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが `--config` で有効なYAML設定ファイルを指定する, **When** ユーザーが日報生成を実行する, **Then** 設定ファイルの内容に従ってLLMモデル、出力先などが反映されて日報が生成される
2. **Given** 設定ファイルに誤った値が記述されている, **When** フレームワークが起動する, **Then** スキーマ検証によりエラーが検出され、どの設定項目が不正かが具体的に報告される
3. **Given** ユーザーが設定ファイルでコンポーネントごとに異なるLLMモデルを指定する, **When** 日報生成が実行される, **Then** 各コンポーネント（収集、解析、レポート生成）が指定されたモデルを使用して処理を行う

---

### Edge Cases

- 前日の日付境界：システムのローカルタイムゾーン（OS設定）に基づいて「前日」を判定する
- ログファイルが巨大な場合：設定可能なタイムアウト（デフォルト600秒）を設け、タイムアウト時は処理済み部分までのデータを採用する。後続のLLM投入時に分割要約される
- 出力ディレクトリが存在しない場合：設定ファイル読み込み時にエラーメッセージを表示して終了する。自動生成は行わない
- 同名の日報ファイルが既に存在する場合：常に上書きする
- データソースのログディレクトリが存在しない/アクセス不能な場合：該当ソースをスキップし、他のソースの処理を継続する
- 複数日にまたがるログが混在する場合：指定日のタイムスタンプでフィルタリングする。単一日付のみサポートのため、日跨がりの範囲指定は発生しない
- LLMのトークン制限を超える入力データ：データを複数チャンクに分割し、各チャンクを個別に要約した後に統合して最終的な日報を生成する
- LLM API呼び出しの一時的エラー（レート制限429、サーバー過負荷503等）：指数バックオフ（初回待機1秒、以後倍加）で最大3回リトライする。全リトライ失敗後は該当LLM呼び出しの失敗としてパイプラインを停止する。永続エラー（認証失敗401、不正リクエスト400/403等）はリトライせず即時停止する

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは指定された日付（デフォルトは前日）のログを複数のデータソースから自動収集しなければならない（MUST）
- **FR-002**: システムは収集したログをLLMにより解析し、開発活動の分類・要約・カテゴリ抽出を行わなければならない（MUST）
- **FR-003**: システムは解析結果から構造化された日報をMarkdown形式で生成し、指定された出力先に保存しなければならない（MUST）
- **FR-004**: システムは `dev-log-daily` コマンドのCLIインターフェースを提供し、コマンド一つで日報生成を実行できなければならない（MUST）
- **FR-005**: システムはパイプラインの実行状況を逐次標準出力に表示し、各ノードの開始・終了・エラーをユーザーに通知しなければならない（MUST）。詳細ログはファイルにも出力可能とする（SHOULD）
- **FR-006**: 各データソース（Copilotチャット、Gitコミット、ターミナル履歴）の収集・解析ロジックは、それぞれ独立したツールモジュールとして実装し、共通のインターフェース（collect/parse）に従わなければならない（MUST）。各ツールはプロダクトに内蔵固定とし、外部からの動的ロードやユーザーによる追加・選択は不可とする（MUST）。
- **FR-007**: システムはYAML形式の設定ファイルにより、LLMモデル選択、出力設定などをカスタマイズ可能としなければならない（MUST）。設定ファイルのパスはCLIオプション `--config` で明示的に指定することを必須とし、指定がない場合は起動時にエラーを報告しなければならない（MUST）。出力ディレクトリは設定ファイルの必須項目であり、指定されたディレクトリが存在しない場合も起動時にエラーを報告しなければならない（MUST）
- **FR-008**: 各データソースツールは独立して動作し、他のツールの障害の影響を受けない設計としなければならない（MUST）
- **FR-009**: 設定値はスキーマにより検証され、不正な設定は起動時に具体的なエラーメッセージでユーザーに通知しなければならない（MUST）
- **FR-010**: 各コンポーネント（Collector、Parser、Enricher、Reporter）は独立したLLMモデルを設定ファイルで指定可能としなければならない（MUST）。すべてのコンポーネントにモデル指定は必須であり、未指定がある場合は起動時にエラーを報告しなければならない（MUST）
- **FR-011**: 収集したログデータおよび生成された日報は、すべてローカルファイルシステム上に保存され、ユーザーがいつでも削除・エクスポート可能でなければならない（MUST）
- **FR-012**: 外部サービスへのデータ送信機能はデフォルトで無効であり、ユーザーが明示的に有効化した場合のみ動作しなければならない（MUST）
- **FR-013**: 初期リリースでは最低限 GitHub Copilotチャットログ、Gitコミット履歴、ターミナル操作履歴 の3つのデータソースに対応しなければならない（MUST）
- **FR-014**: すべての機能追加・変更には対応する単体テストおよび結合テストが実装されなければならない（MUST）
- **FR-015**: ログファイル処理には設定可能なタイムアウト（デフォルト600秒）を設けなければならない（MUST）。タイムアウト発生時は処理済み部分までのデータを保持し、後続のLLM処理で分割要約の対象としなければならない（MUST）

### Key Entities

- **データソースツール（DataSourceTool）**: 特定のデータソースからログを収集・解析する独立したモジュール。収集（collect）と解析（parse）のインターフェースを持つ。プロダクトに内蔵固定の3種類（Copilotチャット、Gitコミット、ターミナル履歴）を提供し、ユーザーによる追加・選択は不可。各ツールのデータパス（リポジトリパス、チャットログディレクトリ、履歴ファイル等）は設定ファイルで指定する。
- **日報（DailyReport）**: 指定日付の開発活動を構造化したMarkdownドキュメント。ファイル名は `daily_report_YYYY-MM-DD.md` の形式。概要、使用技術、学習内容、開発活動、発生した問題と解決策のセクションを含む。
- **設定（Configuration）**: フレームワーク全体の動作を制御するYAML設定情報。データソースリスト、LLMモデルマッピング（各コンポーネントのモデル・ベースURL・APIキーを含む）、出力形式、出力先（必須）などを含む。出力ディレクトリは必須項目であり、存在確認が起動時に行われる。LLM APIキーも設定ファイルに直接記述される。
- **収集ログ（CollectedLog）**: 各データソースから収集された生ログデータ。ファイルパス、タイムスタンプ、データソース種別のメタデータを持つ。
- **解析結果（ParsedData）**: 収集ログをLLMで解析した構造化データ。各データソース固有の形式で保持され、最終的に日報生成の入力となる。
- **パイプラインオーケストレーション**: Collector（収集）→ Parser（解析）→ Enricher（補完）→ Reporter（生成）の各ノードはLangGraph StateGraphにより状態共有しながら順次実行される。Enricherは各データソースの解析結果をクロスリファレンスし、矛盾点の指摘や欠落情報の補完、コンテキストの付与を行う。各ノードの出力はグラフの共有状態（DailyState）に蓄積され、後続ノードが参照可能。各データソースツールはCollectorノード内で並列実行され、各ツールの障害は他のツールに影響しない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーはCLIコマンドの実行から日報ファイルの出力完了までを3分以内で完了できる
- **SC-002**: 日報の内容は、元のログデータの主要な開発活動（使用技術、学習内容、発生した問題）を90%以上カバーしている
- **SC-004**: 1つのデータソースが障害を起こしても、他のデータソースからの日報生成は正常に完了する
- **SC-005**: 設定ファイルの誤りが起動時に100%検出され、修正箇所が具体的に報告される
- **SC-006**: 日報作成にかかる手動作業時間が、本フレームワーク導入前と比較して80%以上削減される

## Assumptions

- ユーザーはローカル環境にLLM API（OpenAI互換またはローカルLLMサーバー）へのアクセス手段を持っている。APIキー・ベースURL等の接続情報はYAML設定ファイルの `llm` セクションに直接記述する
- ユーザーはPython 3.11以上の実行環境を持っている
- データソースのログはローカルファイルシステム上に存在し、読み取り権限がある
- 初期リリースの対象ユーザーは個人開発者であり、マルチユーザー対応は範囲外とする
- スケジュール実行（cron等による定期実行）は本フレームワークの責務外とし、ユーザーがOSの仕組みで対応する
- 日報の出力形式はMarkdownを標準とし、他の形式（PDF、HTML等）への対応は将来の機能拡張とする
- 使用するLLMモデルは各ユーザーが自身で用意・設定する前提とする（モデルの提供は本フレームワークの範囲外）
- 日本語環境を第一対象とし、日報は日本語で生成される
- ログの収集対象はデフォルトで「前日」、CLIオプション `--date` で任意の単一日付を指定可能。複数日の期間指定は範囲外とする
- 「前日」の判定はシステムのローカルタイムゾーン（OS設定）に基づく
- 出力ディレクトリは設定ファイルの必須記載項目であり、存在しない場合はエラーとして報告する（自動生成は行わない）
