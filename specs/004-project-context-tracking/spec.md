# Feature Specification: 日報におけるプロジェクトコンテキストの明確化

**Feature Branch**: `004-project-context-tracking`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "日報を記載する上で、何のプロジェクトに対する作業を実施したのかは明確に記載するようにしてほしい。現状は複数プロジェクトを操作したり、単一で操作した場合でも明確に何というプロジェクトに対する操作を実施したのかが分からなくなっている。"

## Clarifications

### Session 2026-07-21

- **Q**: プロジェクト活動データを DailyState で保持する構造は？ → **A**: プロジェクト名キー辞書 `dict[str, ProjectActivity]` を採用。`project_name` をキーとし、各プロジェクトの活動をデータソース横断で集約する構造とする。Enricher が統合しやすく、Reporter がプロジェクト単位で日報を生成しやすい設計を優先する。
- **Q**: プロジェクト名の表記ゆれ解決に補助的仕組み（設定ファイルのエイリアス等）は必要か？ → **A**: 不要。ユーザーにプロジェクト名を意識させる設計は避け、LLM の推論のみで解決する。LLM が誤統合した場合でも、日報の「(推測)」表記でユーザーが気づけるようにする。
- **Q**: プロジェクト活動データ（`dict[str, ProjectActivity]`）の生成タイミングと責務は？ → **A**: Parser で各ツールが「この活動はプロジェクトXに関する」という生のヒント（`project_hints`）を解析結果に付与し、Enricher が全ソースのヒントをクロスリファレンスして正規化されたプロジェクト辞書を生成する二段構え。Parser は各ソース固有のプロジェクト名候補（ワークスペース名・リポジトリパス名・cwd ディレクトリ名）を抽出し、Enricher が表記ゆれを解決して統合する。
- **Q**: 「📁 作業プロジェクト」セクションの出力粒度と日報全体のフォーマット方針は？ → **A**: プロジェクト名・活動要約・主な成果を含める（オプションC）。さらに、日報全体のフォーマットをプロジェクト単位の構造に変更する。従来のカテゴリ別（技術・ツール／学習内容／開発活動／問題と解決策）ではなく、プロジェクトごとに「そのプロジェクトで何をしたか」「学んだこと」「発生した問題」を記載する形式とする。プロジェクトを跨ぐ横断的な活動（共通の学びや振り返り等）は別途集約セクションとして末尾に設ける。
- **Q**: 既存の日報フォーマットとの互換性はどうするか？ → **A**: 新フォーマットに移行し上書きする。既存 spec（001-auto-daily-report）で「同名ファイルは常に上書き」と定めており、日報は毎回再生成する使い方を前提とするため、新しいプロジェクト単位フォーマットで統一する。
- **Q**: Reporter へのプロジェクト活動データの受け渡し方法は？ → **A**: Enricher が生成した `dict[str, ProjectActivity]` をプロンプトの主要構造として渡す（オプションB）。Reporter は「各プロジェクトのセクションを埋めよ」という編集作業に近い形で日報を生成し、出力の安定性を高める。従来の各ソース別テキストサマリーは補助情報として併用する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロジェクト別に整理された日報の生成 (Priority: P1)

開発者が日報生成を実行すると、生成された日報の「📁 作業プロジェクト」セクションがプロジェクト単位で整理されて出力される。同じプロジェクトに属する GitHub Copilot チャットでの議論、Git コミット、ターミナル操作がグループ化され、どのプロジェクトに対してどのような作業を行ったかが一目で把握できる。開発者は日報を読むだけで、その日に携わった全プロジェクトと、各プロジェクトでの活動内容を理解できる。

**Why this priority**: 本機能の核心価値である「プロジェクトを明確にした日報出力」を実現する最小機能。これにより日報の実用的価値が大幅に向上する。

**Independent Test**: 複数のプロジェクトで活動があった日のデータを入力として日報を生成し、出力された日報にプロジェクト名ごとに活動がグルーピングされて記載されていることを確認する。

**Acceptance Scenarios**:

1. **Given** 前日に複数のプロジェクト（例: DevLogDaily, MyApp, Docs）で開発活動があった, **When** ユーザーが日報生成を実行する, **Then** 日報の「📁 作業プロジェクト」セクションにプロジェクトごとに独立したサブセクションが設けられ、各プロジェクトの活動が整理されて記載される
2. **Given** 前日に単一プロジェクトのみで活動があった, **When** 日報生成を実行する, **Then** そのプロジェクトの活動が「📁 作業プロジェクト」セクションの唯一のサブセクションとして記載され、「単一プロジェクトのみ」であることが分かる形式で出力される
3. **Given** データソース間で同一プロジェクトに対する活動が分散している（Copilot チャット・Git コミット・ターミナル操作が同一プロジェクト）, **When** 日報生成を実行する, **Then** これらが同一プロジェクトの活動として統合されて日報に記載される

---

### User Story 2 - ターミナル操作のプロジェクト情報の可視化 (Priority: P2)

開発者がターミナルで作業すると、各コマンドの実行ディレクトリ（cwd）と Git ブランチ情報がログに記録され、日報生成時に LLM が「どのプロジェクトのどのブランチで実行された操作か」を認識して日報に反映する。これにより、ターミナル操作が単なるコマンドの羅列ではなく、特定プロジェクトの文脈を持った活動として日報に記載される。

**Why this priority**: ターミナル操作は最も頻繁に発生するデータソースだが、現状プロジェクト情報が欠落している。これを補完することで日報の精度が大きく向上する。ただし User Story 1 のプロジェクトグループ化が先に確立している必要があるため P2 とする。

**Independent Test**: ターミナル履歴 JSONL に複数の異なるディレクトリでのコマンドが記録されている状態で日報を生成し、各コマンドがどのプロジェクトのものかが日報に反映されていることを確認する。

**Acceptance Scenarios**:

1. **Given** ターミナル履歴に `cwd` が異なる複数のプロジェクトのコマンドが記録されている, **When** 日報生成を実行する, **Then** 各ターミナル操作が対応するプロジェクトの活動として正しく分類される
2. **Given** ターミナル履歴に `cwd` が同一プロジェクト内で異なるサブディレクトリを移動した記録がある, **When** 日報生成を実行する, **Then** それらが同一プロジェクトの活動として統合される

---

### User Story 3 - プロジェクト横断的な整合性の確認 (Priority: P3)

開発者が日報の「📁 作業プロジェクト」セクションを読むことで、各プロジェクトにおける作業の全体像と、データソース間の整合性を確認できる。例えば、「Copilot チャットで議論した設計が、実際に Git コミットとして実装され、ターミナル操作でテスト実行された」という一連の流れが追跡可能になる。

**Why this priority**: 「プロジェクトを明確にする」という基本要件を超えた、活動のトレーサビリティ向上に関する付加価値機能。User Story 1・2 が先に実装されている必要があるため P3 とする。

**Independent Test**: 同一プロジェクト内で Copilot チャットでの設計議論、実装の Git コミット、テスト実行のターミナル操作があった日のデータを入力とし、日報上でこれらの一連の流れが追跡できる形で記載されていることを確認する。

**Acceptance Scenarios**:

1. **Given** 同一プロジェクトで「Copilot チャットでの設計議論 → Git コミットでの実装 → ターミナルでのテスト実行」の流れがあった, **When** 日報生成を実行する, **Then** これらの活動が同一プロジェクト内で時系列に関連付けられて記載される
2. **Given** あるプロジェクトの活動が一部のデータソースにしか存在しない, **When** 日報生成を実行する, **Then** 欠落しているデータソースについては「該当データなし」と明示される

---

### Edge Cases

- **プロジェクト名の解決競合**: 同一の cwd（カレントディレクトリ）やリポジトリパスが異なるワークスペース名と紐づく場合、LLM が最も適切なプロジェクト名を推定する。推定であることが日報に明記される
- **cwd が存在しない（空値）**: ターミナル履歴に cwd が記録されていないエントリは「プロジェクト不明」として分類され、日報にその旨が明記される
- **大量のプロジェクト**: 1日に10以上のプロジェクトを操作した場合、主要なプロジェクトのみ詳細表示し、その他は一覧表示に切り替わる
- **プロジェクト名の重複**: 同名のプロジェクト名が異なるパスに存在する場合、パスの上位ディレクトリも含めて区別する
- **データソース間でのプロジェクト名の表記ゆれ**: VS Code ワークスペース名（"DevLogDaily"）と Git リポジトリ名（"dev-log-daily"）と cwd 由来の名前（"DevLogDaily"）が異なる場合でも、同一プロジェクトとして正しく統合される

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはターミナル履歴の収集・解析時に各エントリの cwd（カレントディレクトリ）と git_branch 情報を保持し、LLM による解析に渡さなければならない（MUST）
- **FR-002**: 各データソース（Copilot チャット、Git コミット、ターミナル履歴）の Parser は、収集データから活動が属するプロジェクト名の候補を抽出し、`project_hints` として解析結果に含めなければならない（MUST）。Copilot チャットはワークスペース名、Git コミットはリポジトリパス名、ターミナル履歴は cwd ディレクトリ名をそれぞれヒントとして抽出する
- **FR-003**: システムはパイプラインの共有状態（DailyState）に、Parser の `project_hints` を格納するフィールドと、Enricher が統合した正規化済みプロジェクト活動辞書 `dict[str, ProjectActivity]` を格納するフィールドを持たなければならない（MUST）
- **FR-004**: Enricher ノードは Parser から受け取った全データソースの `project_hints` をクロスリファレンスし、表記ゆれを解決した上で同一プロジェクトの活動を統合した正規化済みプロジェクト活動辞書を生成し、後続の Reporter に渡さなければならない（MUST）
- **FR-005**: 日報（Reporter ノード出力）のフォーマットはプロジェクト単位の構造とし、Enricher が生成した `dict[str, ProjectActivity]` を主要入力として受け取り、プロジェクトごとに活動内容・学習内容・発生した問題等を記載しなければならない（MUST）。従来の各ソース別テキストサマリーは補助情報として併用する。以下のセクション構成とする：
  1. ヘッダー（日付・タグ・mood・energy）
  2. 📋 概要（全プロジェクト横断の一日の要約）
  3. 📁 作業プロジェクト（プロジェクトごとの詳細セクション）
     - 各プロジェクトのセクションには以下を含む：
       - プロジェクト名と活動の時間範囲
       - 活動内容の要約（2〜3文）
       - 使用・学習した技術・ツール
       - 学習内容・新しく得た知見
       - 発生した問題と解決策（該当する場合）
       - 主な成果・達成事項（該当する場合）
  4. 🔄 振り返り（全プロジェクト横断）
  5. 📌 翌日へのアクション（全プロジェクト横断）
  6. 🏷 技術タグ（全プロジェクト横断）
- **FR-006**: 複数プロジェクトを操作した場合、日報の「📁 作業プロジェクト」セクションにはプロジェクトごとに独立したサブセクションを設け、各プロジェクトの活動が混在せず明確に区分されて記載されなければならない（MUST）
- **FR-007**: ターミナル履歴の cwd が空または不明なエントリは「プロジェクト不明」として分類され、その旨が日報に明記されなければならない（MUST）
- **FR-008**: 同一プロジェクトに対して複数のデータソースで活動があった場合、それらは統合されて一つのプロジェクトエントリとして日報に記載されなければならない（MUST）
- **FR-009**: データソース間でプロジェクト名の表記ゆれ（例: "DevLogDaily" vs "dev-log-daily"）が存在する場合でも、同一プロジェクトとして正しく統合するための仕組みを持たなければならない（MUST）— 実現方法は LLM による推論のみに委ね、ユーザーによる設定入力を必要としない設計とする
- **FR-010**: すべての機能追加・変更には対応する単体テストおよび結合テストが実装されなければならない（MUST）

### Key Entities

- **プロジェクトヒント（ProjectHint）**: Parser が各データソースから抽出する生のプロジェクト名候補。`project_hints` フィールドとして ParsedData に含まれ、Enricher による統合処理の入力となる。
  - フィールド構造:
    - `source`（str）: データソース種別（`copilot_chat` / `git_commits` / `terminal_logs`）
    - `candidate_name`（str）: 抽出されたプロジェクト名候補（ワークスペース名・リポジトリパス名・cwd ディレクトリ名等）
    - `activity_summary`（str）: 当該プロジェクトでの活動要約
- **プロジェクト活動（ProjectActivity）**: Enricher が全ソースの `ProjectHint` を統合して生成する正規化済みプロジェクト情報。プロジェクト名をキーとする辞書 `dict[str, ProjectActivity]` で DailyState に保持され、Enricher から Reporter に渡される。
  - フィールド構造:
    - `project_name`（str）: プロジェクト名（LLM により正規化され統一された名称）
    - `source_activities`（dict[str, list[str]]）: データソース種別（`copilot_chat` / `git_commits` / `terminal_logs`）をキーとし、各ソースの活動要約テキストのリストを値とする
    - `time_range`（dict）: 活動時間範囲（`start`, `end` を ISO 8601 形式で保持）
    - `related_sources`（list[str]）: 活動が確認されたデータソース種別のリスト
- **作業プロジェクトセクション**: 日報内の「📁 作業プロジェクト」セクション。その日に操作したプロジェクトごとに独立したサブセクションを持ち、各プロジェクトの活動内容・学習内容・発生した問題・主な成果をデータソース横断で記載する。これにより読者は「どのプロジェクトで何をしたか」をプロジェクト単位で把握できる。
- **プロジェクトコンテキスト情報**: 各データソースが保持するプロジェクトに関連するメタデータの総称。Copilot チャットのワークスペース名、Git コミットのリポジトリパス、ターミナル操作の cwd と git_branch を含む。Parser によって `ProjectHint` として抽出され、Enricher が `ProjectActivity` へと統合する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同時に3つ以上のプロジェクトを操作した日の日報において、全プロジェクトの活動がプロジェクト別に明確に区分されて記載される
- **SC-002**: ターミナル履歴の cwd が存在する全エントリが、何らかのプロジェクトに紐づけられて日報に反映される
- **SC-003**: 同一プロジェクトに対する Copilot チャット・Git コミット・ターミナル操作のうち、2つ以上のデータソースに活動がある場合、それらが統合されて一つのプロジェクトエントリとして記載される
- **SC-004**: 日報の「📁 作業プロジェクト」セクションを読んだユーザーが、追加の調査なしに「どのプロジェクトで何をしたか」を理解できる

## Assumptions

- プロジェクト名の統合（表記ゆれ解決）は LLM の推論能力に依存し、完全な一致を保証するものではない。LLM が誤って異なるプロジェクトを統合した場合でも、日報には「(推測)」と明記される
- ターミナル履歴の cwd が常に正しく記録されているとは限らない（シェルの設定やログ収集スクリプトの実装に依存）。cwd がないエントリは「プロジェクト不明」として扱う
- VS Code ワークスペース名は workspace.json から抽出可能であり、ユーザーによる追加設定は不要
- プロジェクト名の解決（表記ゆれ統合）は LLM の推論のみで行い、エイリアスや手動マッピングといったユーザー設定は本機能の範囲外とする。これによりユーザーはプロジェクト名を意識することなくツールを使い続けられる
- 本機能は既存のデータモデル（DailyState）にフィールド追加を行うが、既存フィールドの互換性は維持する
- 既存のパイプラインのノード構成（Collector → Parser → Enricher → Reporter）に変更は加えず、各ノードの内部処理を拡張する
- 日報の Markdown フォーマットは従来のカテゴリ別構成からプロジェクト単位構成に変更する。Reporter ノードのシステムプロンプトとテンプレートを全面的に書き換える必要がある
