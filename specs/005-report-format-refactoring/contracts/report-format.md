# Contract: 日報 Markdown 出力フォーマット

**From**: Reporter ノード
**To**: ファイルシステム（daily_report_YYYY-MM-DD.md）
**Version**: 2.0.0（従来フォーマットからのメジャーアップデート）

## 概要

Reporter ノードが生成する Markdown 日報の出力形式を定義する。
本 contract はファイルシステムに書き出される `.md` ファイルの仕様であり、
ユーザーが直接閲覧・検索することを想定する。

## フォーマット仕様

### 1. YAML フロントマター

日報ファイルの先頭は `---` で区切られた YAML フロントマターとする。

```yaml
---
date: YYYY-MM-DD
tags: [DevLogDaily, LangGraph, Python, SpecKit]
type: daily
mood: productive
energy: 4
aliases: [デイリー学習レポート YYYY-MM-DD]
---
```

| フィールド | 必須 | 型 | 制約 |
|-----------|------|-----|------|
| `date` | MUST | YYYY-MM-DD | 対象日と一致すること |
| `tags` | MUST | YAML リスト | 最大10要素。1要素目は DevLogDaily であること |
| `type` | MUST | str | 固定値 `daily` |
| `mood` | MUST | str | productive / reflective / frustrated 等 |
| `energy` | MUST | int | 1〜5 の範囲 |
| `aliases` | MUST | YAML リスト | 1要素目は `デイリー学習レポート YYYY-MM-DD` |

### 2. タイトル

フロントマター直後、1行空行を挟んで `# デイリー学習レポート - YYYY-MM-DD`。

### 3. 📋 総合概要

- 見出しレベル: `##`
- 内容: その日の開発活動全体を2〜3文で要約
- データがない場合: 「該当なし」と記載

### 4. 📊 プロジェクト別活動サマリー

- 見出しレベル: `##`
- Markdown テーブル形式、4列固定

```markdown
| プロジェクト | 活動時間 | 主な活動内容 | 関連データソース |
|------------|---------|-------------|----------------|
| プロジェクトA | 03:15 | 〜の実装、〜の調査 | Copilot, Git, Terminal |
| プロジェクトB | 01:30 | 〜の修正 | Git, Terminal |
```

- 活動時間は継続時間（duration）を HH:MM 形式で表示
- データがない場合: テーブルヘッダーのみ出力（行なし）
- ヘッダー行とセパレータ行は常に出力

### 5. プロジェクト詳細セクション

プロジェクトごとに `## プロジェクト名` の見出しでセクションを分割する。
各プロジェクトセクションは以下のサブセクションを持ち、見出しレベルは `###` を使用する。

```markdown
## プロジェクトA

### 📋 概要
プロジェクトでの活動を2〜5文で要約。

### 🛠 触れた技術・ツール
- **技術名**: 使用目的と学んだこと

### 📖 インプット
読んだ記事、見たコード、参考資料。該当なしの場合は「該当なし」。

### 📚 学習内容
#### 新しく学んだこと
- **学習トピック**: 内容
  - キーポイント: 補足

#### 理解を深めたこと
- **学習トピック**: 内容
  - キーポイント: 補足

### 💻 開発活動
- `feat` ユーザー認証機能を実装 — 関連ファイル: src/auth.py / コミット: abc1234
- `fix` ログイン時のクラッシュを修正 — 関連ファイル: src/auth.py / コミット: def5678
- `docs` API仕様書を更新 — 関連ファイル: docs/api.md
- `chore` 依存パッケージを更新 — 関連ファイル: package.json

### 🚧 発生した問題と解決策
- **問題**: 要約 → **原因**: 原因 → **解決**: 解決方法（`解決済`）
- **問題**: 要約 → **原因**: 原因 → **解決**: 解決方法（`未解決`）

### 🔄 振り返り
#### うまくいったこと
- 具体的な内容

#### 改善したいこと
- 具体的な内容

#### 明日に活かしたい知見
- 具体的な内容

### 📌 翌日へのアクション
- [ ] 優先度の高いタスク
- [ ] 継続して取り組むタスク

### 🏷 技術タグ
`タグ1` `タグ2` `タグ3`
```

#### サブセクションの省略ルール

- `📖 インプット`: 該当データがない場合「該当なし」と明示（セクションは省略しない）
- `🚧 発生した問題と解決策`: 該当データがない場合、セクションごと省略して良い
- `🔄 振り返り`: 該当データがない場合、セクションごと省略して良い
- `📌 翌日へのアクション`: 該当データがない場合、セクションごと省略して良い
- `#### 新しく学んだこと` / `#### 理解を深めたこと`: 該当データがない場合、サブセクションごと省略して良い

#### 活動種別ラベル

| ラベル | 意味 | 使用例 |
|--------|------|--------|
| `feat` | 機能追加・新規実装 | 新機能の実装、モジュール追加 |
| `fix` | 修正・バグ修正 | バグ修正、動作不具合の対応 |
| `docs` | ドキュメント | README更新、コメント追加、仕様書作成 |
| `chore` | その他 | 環境構築、依存更新、リファクタリング |

#### 問題ステータス

| ステータス | 意味 |
|-----------|------|
| `解決済` | 問題が完全に解決した |
| `未解決` | 問題が未解決のまま |
| `一時対処` | 暫定的な対処を行った |

### 6. 「その他」セクション

プロジェクトに紐づかない活動（環境構築・ツール導入・調査等）を集約する。
見出しレベルは `##`、プロジェクト詳細セクションと同一構造だが、以下を除外する：
- `🔄 振り返り`
- `📌 翌日へのアクション`
