# Feature Specification: 日報出力フォーマットの大幅リファクタリング

**Feature Branch**: `005-report-format-refactoring`

**Created**: 2026-07-22

**Status**: Draft

**Input**: User description: "大幅なリファクタリングを実施したいです。日報の出力フォーマットを修正したいです。

新フォーマットはプロジェクトごとに詳細なセクション（概要、触れた技術・ツール、インプット、学習内容、開発活動、発生した問題と解決策、振り返り、翌日へのアクション、技術タグ）を持ち、全プロジェクト横断の総合概要・プロジェクト別活動サマリーテーブル・YAMLフロントマター（date, tags, type, mood, energy, aliases）を含む構造とする。"

## Clarifications

### Session 2026-07-22

- **Q**: 📊 プロジェクト別サマリーテーブルの「活動時間」列は何を表すか？ → **A**: 活動の継続時間（duration）。例: `03:15` で3時間15分の合計作業時間を示す。開始〜終了時刻ではなく、そのプロジェクトに費やした総時間を表す。
- **Q**: 「その他」セクションの「簡略版」構造はどのサブセクションを含むか？ → **A**: 概要・触れた技術・ツール・開発活動・発生した問題と解決策・技術タグに加え、簡易的な学習内容を含める。振り返りと翌日へのアクションは除外する（プロジェクトに紐づかない活動のため）。
- **Q**: Enricher 出力の mood/energy/tags は enriched_data のどこに格納するか？ → **A**: `report_metadata` サブオブジェクトとして集約する。ルートレベルに `"report_metadata": {"mood": "productive", "energy": 4, "tags": ["DevLogDaily", ...], "project_moods": {"ProjectA": {"mood": "...", "energy": 3}}}` を追加する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロジェクト単位に整理された日報の生成 (Priority: P1)

開発者が日報生成を実行すると、新しい出力フォーマットに従ったMarkdown日報が生成される。各プロジェクトの活動が独立したセクションとして整理され、総合概要・プロジェクト別サマリーテーブル・プロジェクトごとの詳細（学習内容・開発活動・問題解決・振り返り・アクション）が構造化されて出力される。YAMLフロントマターには日付・タグ・mood・energy・aliasesが自動設定される。

**Why this priority**: 本リファクタリングの核心である「新しい日報フォーマットの出力」を実現する最小機能。このフォーマット変更がなければ他の付随的な改善の価値が発揮されない。また、004（プロジェクトコンテキスト追跡）で導入したプロジェクト単位のグループ化を前提として、よりリッチなプロジェクト別セクションを出力する。

**Independent Test**: 複数プロジェクトの活動データを入力として日報生成を実行し、出力されたMarkdownファイルが新しいフォーマット仕様に完全に準拠していることを確認する。YAMLフロントマターのパース、セクション構造の検証、各プロジェクトサブセクションの存在確認を行う。

**Acceptance Scenarios**:

1. **Given** 前日に複数プロジェクトで開発活動があった, **When** ユーザーが日報生成を実行する, **Then** 出力された日報に以下の構造がすべて含まれる：
   - 有効なYAMLフロントマター（date, tags, type, mood, energy, aliases）
   - 「# デイリー学習レポート - YYYY-MM-DD」の見出し
   - 「📋 総合概要」セクション（活動全体の2〜3文の要約）
   - 「📊 プロジェクト別活動サマリー」テーブル（プロジェクト名・活動時間・主な活動内容・関連データソース）
   - プロジェクトごとの詳細セクション（上記新フォーマットの全項目を含む）
   - プロジェクトに紐づかない活動の場合は「その他」セクション
2. **Given** 前日に単一プロジェクトのみで活動があった, **When** 日報生成を実行する, **Then** 📊 サマリーテーブルに1行のみのプロジェクトが表示され、該当プロジェクトの詳細セクションのみが出力される
3. **Given** 前日に全くデータがない, **When** 日報生成を実行する, **Then** YAMLフロントマターを含む空の日報が生成され、各プロジェクトセクションが「該当なし」で埋められる

---

### User Story 2 - プロジェクト別振り返りと翌日アクションの出力 (Priority: P2)

開発者が日報を読むと、各プロジェクトの「振り返り」サブセクション（うまくいったこと・改善したいこと・明日に活かしたい知見）と「翌日へのアクション」サブセクションがプロジェクト単位で記載されている。これにより、プロジェクトごとに何が良かったか・次に何をすべきかが明確になる。

**Why this priority**: 新フォーマットの付加価値機能。プロジェクト別の振り返りとアクションは、日報を「単なる活動ログ」から「学習と成長のためのツール」へと昇華させる。ただし、User Story 1 の基本フォーマット出力が先に確立している必要があるため P2 とする。

**Independent Test**: 複数プロジェクトの活動データを入力として日報を生成し、各プロジェクトセクション内に「🔄 振り返り」と「📌 翌日へのアクション」が含まれていることを確認する。

**Acceptance Scenarios**:

1. **Given** 1つのプロジェクトで複数の開発活動があった, **When** 日報生成を実行する, **Then** 該当プロジェクトのセクション内に「🔄 振り返り」サブセクション（うまくいったこと・改善したいこと・明日に活かしたい知見）が記載される
2. **Given** あるプロジェクトで問題が発生し解決した記録がある, **When** 日報生成を実行する, **Then** 該当プロジェクトの「🚧 発生した問題と解決策」サブセクションに問題・原因・解決方法が（`解決済`）マーク付きで記載される
3. **Given** あるプロジェクトに明示的に継続すべき作業がある, **When** 日報生成を実行する, **Then** 該当プロジェクトの「📌 翌日へのアクション」サブセクションにチェックリスト形式でアクションが記載される

---

### User Story 3 - フロントマターとタグによる日報の検索性向上 (Priority: P3)

開発者が生成された日報のMarkdownファイルを開くと、YAMLフロントマターに日付・タグ・mood・energy・aliasesが自動設定されている。これらのメタデータにより、ファイルシステムや検索ツールでの日報の検索・フィルタリングが容易になる。

**Why this priority**: フロントマターは既存のREPORTER_SYSTEM_PROMPTでも一部対応済みだが、新フォーマットで正式に仕様として確立する。検索性向上はユーザー価値があるが、日報の中身自体には影響しないため P3 とする。

**Independent Test**: 日報ファイルをYAMLパーサーで読み込み、フロントマターの各フィールド（date, tags, type, mood, energy, aliases）が有効な値を持っていることを検証する。

**Acceptance Scenarios**:

1. **Given** 日報が生成された, **When** そのMarkdownファイルをYAMLパーサーで解析する, **Then** frontmatterの `date` が対象日と一致し、`tags` がリスト形式で、`type` が `daily`、`mood` と `energy` が有効値（mood: productive/reflective/frustrated 等、energy: 1-5）で、`aliases` がリスト形式で出力される
2. **Given** データからmoodやenergyを推測できる十分な情報がある, **When** 日報生成を実行する, **Then** フロントマターのmoodとenergyがデータから推測された値に設定される。推測できない場合はデフォルト値（mood: productive, energy: 4）が設定される

---

### Edge Cases

- **全データソースが空**: YAMLフロントマターのみを含むベース日報を生成し、全プロジェクトセクションを「該当なし」で埋める。旧フォーマットの空日報（`_generate_empty_report`）を新フォーマットに更新する必要がある
- **プロジェクト数が10以上**: 📊 サマリーテーブルには全プロジェクトを表示するが、詳細セクションは主要なプロジェクトのみ詳細表示し、残りは一覧表示に切り替える。この閾値はLLMの判断に委ねる
- **「その他」カテゴリしかない日**: プロジェクトに紐づかない活動（環境構築・ツール導入等）のみの日は、「その他」セクションのみが出力される。📊 サマリーテーブルの「プロジェクト」列には「その他」と表示される
- **プロジェクト内の特定サブセクションに該当データがない場合**: サブセクション種別ごとに以下のルールで出力する：
  - 「📖 インプット」：該当データがなくても「該当なし」と明示する（セクション省略不可）
  - 「🚧 発生した問題と解決策」「🔄 振り返り」「📌 翌日へのアクション」：データがない場合、セクションごと省略して良い
  - 「#### 新しく学んだこと」「#### 理解を深めたこと」：データがない場合、サブセクションごと省略して良い
- **mood/energyの推測が困難な場合**: データからmoodやenergyを推測できない場合はデフォルト値（mood: productive, energy: 4）を設定し、日報内で「(推測)」と明記しない。フロントマターは常に有効な値を保つ
- **タグが多すぎる場合**: フロントマターのtagsはデフォルトタグ（DevLogDaily, LangGraph, Python, SpecKit）＋プロジェクト横断で重要なタグを最大10個までに制限する。プロジェクト個別のタグは各プロジェクトセクションの「🏷 技術タグ」に記載する

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Reporter ノードが出力する日報の Markdown フォーマットを、以下の新構造に変更しなければならない（MUST）。従来のカテゴリ別構成（🛠 本日触れた技術・ツール、📚 学習内容、💻 開発活動をトップレベルで分割）から、プロジェクト単位の入れ子構造に変更する：
  - YAML フロントマター（date, tags, type, mood, energy, aliases）
  - "# デイリー学習レポート - YYYY-MM-DD" 見出し
  - "📋 総合概要"：一日の活動全体を2〜3文で要約
  - "📊 プロジェクト別活動サマリー"：Markdownテーブル形式（プロジェクト名、活動時間（継続時間）、主な活動内容、関連データソースの4列）。活動時間は合計作業時間（例: `03:15` で3時間15分）を HH:MM 形式で表示する
  - プロジェクトごとの詳細セクション（見出しレベル「## プロジェクト名」）：
    - "📋 概要"：プロジェクト内活動の2〜5文の要約
    - "🛠 触れた技術・ツール"：使用した技術と学んだこと
    - "📖 インプット"：読んだ記事・参考資料（該当なしの場合は「該当なし」）
    - "📚 学習内容"：
      - "#### 新しく学んだこと"：新たに得た知識
      - "#### 理解を深めたこと"：既存知識の深化
    - "💻 開発活動"：種別（feat/fix/docs/chore）付き箇条書き（関連ファイル・コミットハッシュを含む）
    - "🚧 発生した問題と解決策"：問題・原因・解決方法（`解決済`/`未解決`/`一時対処`）
    - "🔄 振り返り"：
      - "#### うまくいったこと"
      - "#### 改善したいこと"
      - "#### 明日に活かしたい知見"
    - "📌 翌日へのアクション"：チェックリスト形式
    - "🏷 技術タグ"：プロジェクト固有のタグ
  - 「その他」セクション（プロジェクトに紐づかない活動用、簡略版構造）。以下を含む：
    - "📋 概要"
    - "🛠 触れた技術・ツール"
    - "📚 学習内容"（簡易版）
    - "💻 開発活動"
    - "🚧 発生した問題と解決策"
    - "🏷 技術タグ"
    - 「🔄 振り返り」「📌 翌日へのアクション」はプロジェクトに紐づかない活動のため除外する
- **FR-002**: REPORTER_SYSTEM_PROMPT 定数を全面的に書き換え、新しいフォーマット指示に更新しなければならない（MUST）。旧フォーマットのセクション指示（⏱ タイムトラッキング、🛠 本日触れた技術・ツール 等）をすべて新フォーマットの指示に置き換える
- **FR-003**: `_generate_empty_report()` 関数の出力フォーマットを新しい構造に更新しなければならない（MUST）。全データが空の場合でも、YAMLフロントマター・総合概要（「該当なし」）・プロジェクト別サマリーテーブル（空）・プロジェクト詳細（「該当なし」）を含む完全なフォーマットの日報を生成する
- **FR-004**: Reporter ノードの LLM プロンプトテンプレート（REPORTER_PROMPT_TEMPLATE）に、新フォーマットで必要となる追加コンテキスト（プロジェクトごとの時系列情報等）を渡せるように拡張しなければならない（MUST）。ただし、テンプレート変数自体の追加は最小限に留め、主要入力は引き続き project_activities とする
- **FR-005**: Enricher ノードの出力（enriched_data）に、新フォーマットで必要な以下の情報が含まれるように拡張しなければならない（MUST）。これらの情報は `enriched_data["report_metadata"]` に ReportMetadata サブオブジェクトとして集約する：
  - プロジェクト横断の全体的な mood/energy の推定値（デフォルト: productive / 4）
  - フロントマター用の tags 候補（デフォルトタグ＋活動内容から抽出、最大10個）
  - プロジェクトごとの mood/energy の推定値（`project_moods` キーにプロジェクト名をキーとする辞書。各値は `{"mood": "productive", "energy": 4}` 形式）
  - プロジェクトごとの活動時間範囲（start/end）の精度向上
  - プロジェクトごとの「振り返り」と「翌日へのアクション」に必要な文脈情報（問題の解決状況、未完了タスク等）
  - enriched_data の JSON 構造例：
    ```json
    {
      "cross_references": [...],
      "contradictions": [...],
      "completions": [...],
      "context": "...",
      "key_activities": [...],
      "projects": {...},
      "report_metadata": {
        "mood": "productive",
        "energy": 4,
        "tags": ["DevLogDaily", "Python", "LangGraph"],
        "project_moods": {
          "ProjectA": {"mood": "frustrated", "energy": 3},
          "ProjectB": {"mood": "productive", "energy": 5}
        }
      }
    }
    ```
- **FR-006**: Parser ノードの LLM プロンプトが、新フォーマットの「💻 開発活動」セクションで必要となる以下の情報を抽出できるようにしなければならない（MUST）。活動種別の分類は LLM の推論に委ね、Parser でのハードコードによる種別判定は行わない（Assumptions 参照）：
  - 活動種別（feat/fix/docs/chore）の分類（LLM 推論）
  - 関連ファイルパス
  - コミットハッシュ（Gitデータソースから）
- **FR-007**: 設定ファイルに日報フォーマットの出力オプションが不要な場合でも、既存の設定スキーマ（AppConfig）との互換性を維持しなければならない（MUST）。新しいフォーマットはハードコードされたデフォルトとして動作し、設定による切り替えは不要とする
- **FR-008**: すべての機能追加・変更には対応する単体テストおよび結合テストを実装しなければならない（MUST）。具体的には以下を含む：
  - Reporter の単体テスト：新しい日報フォーマットが正しく生成されることの検証（YAMLフロントマターのパース、セクション構造の検証、空データ時の動作確認）
  - Enricher の単体テスト：mood/energy/tags の推定値が enriched_data に含まれることの検証
  - 結合テスト：パイプライン全体を通じて新フォーマットの日報が生成されることの確認
  - 既存テストの更新：フォーマット変更により期待値が変わったテストケースを修正

### Key Entities *(include if feature involves data)*

- **日報フォーマット（ReportFormat）**: Reporter ノードが出力する Markdown ドキュメントの構造定義。YAML フロントマターとプロジェクト単位の入れ子セクションから構成される。従来のフラットなカテゴリ別構成から、プロジェクト別の階層構造に変更される。
- **活動種別（ActivityType）**: 各開発活動の種別ラベル。`feat`（機能追加）、`fix`（修正）、`docs`（ドキュメント）、`chore`（その他）の4種。従来の自由記述形式から、種別ラベル付きの構造化された箇条書きに変更される。
- **プロジェクト別振り返り（ProjectRetrospective）**: 各プロジェクトセクション内の「🔄 振り返り」サブセクション。うまくいったこと・改善したいこと・明日に活かしたい知見の3項目をプロジェクト単位で保持する。従来は全プロジェクト横断で1回のみ出力していたものを、プロジェクトごとに分割する。
- **YAMLフロントマター（Frontmatter）**: 日報ファイル先頭の YAML メタデータ。date（対象日）、tags（デフォルトタグ＋活動由来のタグ）、type（固定値 "daily"）、mood（データから推定）、energy（1-5の数値）、aliases（エイリアス用リスト）の6フィールドで構成される。
- **プロジェクト別活動サマリーテーブル（ProjectSummaryTable）**: 「📊 プロジェクト別活動サマリー」セクションの Markdown テーブル。プロジェクト名・活動時間・主な活動内容・関連データソースの4列を持ち、すべてのプロジェクトを一覧表示する。新フォーマットで新設される。
- **「その他」セクション（OtherSection）**: プロジェクトに紐づかない活動（環境構築・ツール導入・調査等）を集約するセクション。プロジェクト詳細セクションと同様の構造を持つが、簡略化が許容される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 出力された日報の Markdown を YAML パーサーとセクションパーサーで検証したとき、フロントマターの全フィールドが有効な値を持ち、すべての必須セクションが正しい見出しレベルで存在する
- **SC-002**: 複数プロジェクトの活動データから生成した日報において、各プロジェクトの活動が正しくグループ化され、プロジェクト別サマリーテーブルの行数が実際のプロジェクト数と一致する
- **SC-003**: 全データソースが空の場合でも、エラーなく日報が生成され、出力ファイルが有効な Markdown としてパース可能である（YAML フロントマター + 空セクションを含む完全なフォーマット）
- **SC-004**: 「💻 開発活動」セクションの各エントリが `種別 内容 — 関連ファイル: パス / コミット: ハッシュ` の形式に従っており、データソースから抽出可能な情報が欠落なく含まれている
- **SC-005**: 新フォーマット移行後も、既存のパイプラインエラーハンドリング（LLM エラー時のリトライ・停止、空データ時のスキップ等）がすべて正常に動作する
- **SC-006**: 新フォーマットで生成された日報を読んだ開発者が、追加の調査なしに「どのプロジェクトで何をしたか」「何を学んだか」「何が問題だったか」「次に何をすべきか」を各プロジェクト単位で理解できる

## Assumptions

- 004（プロジェクトコンテキスト追跡）が完了しており、Parser による `project_hints` の抽出と Enricher による `project_activities`（`dict[str, ProjectActivity]`）の生成が正常に動作していることを前提とする
- プロジェクト名の統合（表記ゆれ解決）は 004 の仕様通り LLM の推論に委ねられており、本リファクタリングではこの機構を変更しない
- YAML フロントマターの `mood` と `energy` は LLM がデータから推定する。推定が困難な場合はデフォルト値（mood: productive, energy: 4）を使用する。これらの値をユーザーが手動設定する機能は本リファクタリングの範囲外とする
- 日報のファイル命名規則（`daily_report_YYYY-MM-DD.md`）は変更せず、既存の仕様を維持する
- 既存のパイプラインのノード構成（Collector → Parser → Enricher → Reporter）と LangGraph StateGraph によるオーケストレーション方式は変更しない
- 設定ファイル（config.yml）のスキーマは変更しない。新しいフォーマットはハードコードされたデフォルトとして動作し、フォーマット切り替え用の設定項目は追加しない
- 「💻 開発活動」の活動種別（feat/fix/docs/chore）は LLM がデータから推論して付与する。Parser でのハードコードによる種別判定は行わない
- 「プロジェクト別振り返り」と「翌日へのアクション」は、LLM が Enricher の出力（enriched_data）と各データソースの解析結果から推論して生成する。これらの推論に必要なコンテキストが不足している場合、当該サブセクションは「データ不足のため推論できませんでした」と記載することを許容する
- 本リファクタリングでは古いフォーマットとの互換性は維持しない。既存の日報ファイルは次回生成時に新しいフォーマットで上書きされる
